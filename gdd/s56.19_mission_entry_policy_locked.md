# 56.19 Mission Entry Policy — LOCKED

Owner-approved 2026-06-06. Defines how a player-character enters an ASCII-map
mission (s56) for a given quest seed. Two entry modes, classified per seed type.

## Entry modes

- **AUTO** — the threat comes to the PC, or erupts where they stand. The mission
  is unavoidable and launches on contact/arrival (the zone flips to turn-based by
  the normal s40.x rule once an enemy reaches ALERT).
- **PLAYER_INITIATED** — a known, located threat the PC chooses to assault. The
  mission launches only when the player commits to it.

## Classification (LOCKED)

| Quest seed | Entry mode | Rationale |
|---|---|---|
| Road Encounter | AUTO | travel ambush |
| Ronin / Bandit | AUTO | bandit ambush |
| Oni Manifestation | AUTO | erupts where the PC stands |
| Taint Manifestation | AUTO | erupts like an oni |
| Maho Cult | PLAYER_INITIATED | assault a known cult cell |
| Urban Criminal Network | PLAYER_INITIATED | raid a known hideout |
| Nezumi Infestation | PLAYER_INITIATED | go clear the warren |
| Peasant Revolt | PLAYER_INITIATED | deliberate suppression |
| Wall Sortie | PLAYER_INITIATED | the PC chooses to sortie out |

Unknown / unrecognized seed types default to **PLAYER_INITIATED** — the safe
choice, so an unrecognized seed never auto-launches combat without the player
committing to it.

## Entry mechanism (LOCKED, owner-approved 2026-06-06)

Mission entry is **PC-only**. NPCs never use the ASCII map (hard constraint), and PCs
never run through the NPC decision engine (s60), so mission entry is NOT an NPC ActionID
and does not touch the NPC pipeline (no context lists, no objective_alignment, no NPC
executor).

- **AUTO trigger — on province arrival.** When a PC arrives in (or is present in) a
  province that has an active AUTO seed, that mission launches. The classification is
  read via `MissionEntryController.get_auto_launch_seeds()`; the consuming UI/session
  layer builds the session and calls `CombatScreen.start_mission()`.

  **Arrival trigger events (owner-set 2026-07-21).** "Arrival" fires on all three of:
  travel completion (the PC finishes moving into a new province), province-boundary
  crossing (any move that enters a new province, including mid-journey pass-through),
  and login (the PC reappears at `home_settlement_id` per s60.3). All three reduce to a
  single rule — *the PC is now in a province it was not in the last time arrival was
  evaluated* — so the engine implements them as one province-change check, not three
  separate hooks. Logged-out state (s60.4, `physical_location` = "") counts as "no
  province", so a subsequent login always registers as a fresh arrival.
- **PLAYER_INITIATED — `ENGAGE_MISSION`, 1 AP.** A single PC action launches any
  located player-initiated mission at the PC's current location. It costs **1 AP**, spent
  from the PC's banked-AP pool (s60.5). `MissionEntryController.engage_mission(pc, seed)`
  validates (PC actor, seed is player-initiated, AP available), spends 1 banked AP, and
  returns a launch request the UI consumes.

## Implementation

- `simulation/mission_entry_policy.gd` (MissionEntryPolicy): `entry_mode_for(seed_type)`,
  `is_auto(seed_type)`, `is_player_initiated(seed_type)`. Seed type ints are defined by
  RosterCompositionSystem (Maho Cult = 0 … Wall Sortie = 100) and QuestSeedSelector
  (Oni Manifestation = 101, Road Encounter = 102).
- `simulation/mission_entry_controller.gd` (MissionEntryController, PC-only):
  `get_auto_launch_seeds()`, `get_engageable_seeds()`, `can_engage_mission()`,
  `engage_mission()`, `ENGAGE_MISSION_AP_COST = 1`.
- `simulation/pc_system.gd`: `can_spend_banked_ap()` / `spend_banked_ap()` (s60.5).

- `simulation/mission_launcher.gd` (MissionLauncher): `build_session(seed, province,
  province_history, seed_str, player)` — the headless half of the launch, turning a launch
  request into a ready `MissionSession` (Water Ring = min(Strength, Perception)). Returns null
  when the roster is not ready or the session is invalid.

## UI/session glue

`scripts/ui/mission_flow.gd` (MissionFlow, extends Node) is the UI/session glue: it owns a
`CombatScreen` and drives entry — `on_pc_arrived(pc, province, province_history, active_seeds,
seed_str)` auto-launches the first AUTO seed and returns the engageable PLAYER_INITIATED seeds;
`engage(pc, seed, …)` fires ENGAGE_MISSION (spends 1 banked AP) and launches. It builds the
session via `MissionLauncher` and calls `CombatScreen.start_mission()`, relaying
mission_complete / player_died / mission_blocked. ⚠ Written without a Godot runtime — unverified;
review and run under Godot/GUT before relying on it.

## Arrival-detection core (built 2026-07-21)

`simulation/pc_arrival_resolver.gd` (PCArrivalResolver) is the headless, network-free core
of the arrival trigger. `resolve_arrival(pc, …)` is PC-only (refuses any non-PC via
`PcSystem.is_valid_pc`), computes the PC's current province from `physical_location`
(settlement → province), compares it to the last-processed province
(`L5RCharacterData.last_arrival_province_id`), and on a change returns that province's
seeds already classified into AUTO / PLAYER_INITIATED (`QuestSeedSelector.select_province_seeds`
+ `MissionEntryController`). It only decides and classifies — it does not launch (that stays
`MissionFlow` / `CombatScreen`) and does not touch networking.

## Remaining dependency (not yet built)

The remaining missing piece is the **PC MUD-travel / navigation layer** that mutates
`physical_location` (and so drives PCArrivalResolver → `MissionFlow.on_pc_arrived` →
`CombatScreen.start_mission`). Per s4.4 this is MUD zone navigation (Greater → Navigation →
Lesser zones), a player-facing networking/UI system; it does not exist yet. Zone-level (finer
than province) AUTO triggering is likewise deferred (s4.4/s60 PC zone position tracking).
